# synap iPhone recorder

Native SwiftUI + CoreBluetooth capture for iPhone/iPad (iOS 16 or newer). The Bluetooth delegate and disk journal run on a dedicated serial queue. iOS background Bluetooth delivery does not depend on a Bluefy page, JavaScript timer or visible recording screen.

## Use

1. Update the C3/S3 pendant to `synap-os1-build1205` or newer through the existing Synap firmware updater.
2. Disconnect Bluefy, then connect the pendant in this app. Use one recorder at a time.
3. Tap **Start recording** or double-tap the pendant after the app says Ready. Switch apps or lock the screen; received packets continue to be handled by CoreBluetooth.
4. Tap **Stop & save** or double-tap the pendant. The app waits for the firmware to drain before closing the WAV. The clock counts complete received frames; missing positions stay silent and are reported.
5. Open a saved recording to listen or **Share original WAV → Save to Files**. In the Synap web app, use **Library → Import audio**, select that WAV, then **Process** under your signed-in account.

The native recorder stores locally; it does not yet authenticate to Synap Cloud or upload automatically. Import is an explicit handoff. Source PCM is neither denoised, normalized, gated, resampled nor re-encoded. Supported BLE links use 16 kHz mono PCM16; the firmware may use its independent-frame ADPCM fallback at a smaller negotiated MTU. Decoding ADPCM cannot restore information already lost on that transport.

## Build and install

Open `SynapRecorder.xcodeproj` on a Mac with Xcode 16 or newer. Choose the SynapRecorder target, select your Apple development team under Signing & Capabilities, and use a bundle identifier registered to that team. Connect your iPhone, enable Developer Mode if requested, select it as the destination, then Run. Signing and provisioning are intentionally not committed.

For TestFlight, archive using the team's distribution signing and upload through Xcode Organizer/App Store Connect. The unsigned CI archive is a build-verification artifact; it cannot be installed directly or treated as a signed IPA.

```sh
swift test --package-path native/ios
xcodebuild -project native/ios/SynapRecorder.xcodeproj -scheme SynapRecorder \
  -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

CI also builds an unsigned Release archive for a physical iOS target. Core tests exercise exact PCM, an ADPCM golden vector generated by the existing browser codec, counter wrap, late and duplicate frames, malformed chunks, session ownership, pending-chunk restoration and interrupted disk writes. Simulator/build results do not validate real Bluetooth radio behavior.

## Storage and recovery

Each take has `packets.synap` (original timestamped BLE notifications with per-record CRC32), `recording.wav` and an atomic `checkpoint.json`. Every packet is appended before decoding; WAV and journal are synchronized every 64 packets and on lifecycle/stop checkpoints. Checkpoints retain incomplete frames and the replay cursor. A relaunch replays the uncheckpointed tail; a torn final write is retained separately. Disk-full/corrupt-journal failures retain files and stop accepting a new take until recovery succeeds. Small amounts of unflushed data can still be lost on abrupt power loss.

Files use `completeUntilFirstUserAuthentication`, so writes remain possible with the screen locked after the first unlock following boot. They are excluded from device backups; export important takes. iOS state restoration uses a stable central identifier and the persisted active take. A resumed stream must match peripheral UUID, pendant identity, recovery token and stream generation. Reconnecting never sends START. Already-completed frames are deduplicated; available late frames fill their original positions.

The WAV contains standard PCM plus an optional `syap` RIFF chunk with take ID, original timestamp, device ID, frame counts and marked moments. It does **not** export the recovery token. The web import validates this metadata and always derives cloud ownership from the current signed-in account.

## Physical-device acceptance (required before calling background capture verified)

Use both C3 and S3 with a repeatable audible time signal and save a comparison recording:

- Record 2 minutes in foreground, 10 minutes in another app, 10 minutes with the screen locked, then 2 minutes in foreground. The source WAV must contain the entire audible sequence. Inspect received/missing frame counts and negotiated PCM/fallback transport.
- Repeat in Low Power Mode. Watch battery, heating, disk growth and packet loss for a 60-minute take. PCM plus original packets uses roughly 230–250 MB/hour; measure on the actual link.
- Move out of range briefly, return, stop while disconnected, and double-tap Stop while locked. Verify the same take resumes/drains, gaps remain visible and no second START occurs. Firmware buffering is bounded: C3 about 1.25 seconds; S3 with PSRAM about 30 seconds. Longer radio outages cannot be recovered completely.
- Interrupt the process through an OS termination/restoration exercise and relaunch. Check received audio and partial-frame recovery. An explicit user force-quit, Bluetooth being disabled, a reboot before unlock, or exhausted storage prevents continued capture. Native background mode is not an unlimited execution guarantee.
- Export, import into the signed-in web app, process, and compare the stored/imported source WAV bytes. Inspect marked moments and timestamps around a deliberate gap.

No microphone permission, silent-audio keepalive or background-audio entitlement is used. No physical C3/S3 + iPhone background test has been performed by CI.

Apple references: [Core Bluetooth background processing and restoration](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html), [file protection after first unlock](https://developer.apple.com/documentation/foundation/fileprotectiontype/completeuntilfirstuserauthentication).
